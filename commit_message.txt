feat(worker): restore rate limiting (WorkerOptions.limiter)

Restore the rate limiter logic that was stripped from the Lua scripts
relative to upstream BullMQ v5, keeping the repo-specific marker
adaptations intact.

- Add WorkerOptions.limiter (RateLimiterOptions { max, duration }) and
  WorkerBuilder::limiter(...).
- Port upstream includes/getRateLimitTTL.lua as a flat include and
  register it in the script loader.
- moveToActive-11.lua: use the previously-unused limiter key (KEYS[6]),
  accept limiter max/duration as ARGV[6]/ARGV[7], return
  {0, 0, rateLimitedNextTtl, 0} when limited, and INCR + PEXPIRE the
  limiter counter when handing out a job (same wire format as upstream
  prepareJobForProcessing, so Node and Rust workers can cohabit).
- moveToFinished-14.lua: same limiter handling in the fetchNext path
  (ARGV[11]/ARGV[12]).
- Worker loop: pass limiter opts to moveToActive/moveToFinished, parse
  the rate-limited response (MoveToActiveResult.rate_limit_ttl) and
  sleep until the TTL expires (bounded, shutdown-aware) instead of
  hammering Redis; the marker is restored after the sleep so waiting
  jobs are picked up immediately.
- Integration tests: throughput is capped with limiter {max:2, 2s}
  (≤2 completed after 1s, all 6 within 10s) and unchanged fast path
  without a limiter.
